## 1. PR #116 — stop the request storm (`c7f7368`, 2026-07-24)

**What went wrong.** `pg_stat_statements` showed `set_config('search_path', …)` at
**683,878,980 calls — 59.9% of database time** against ~160K real queries, with DB CPU at
91%. Root cause in the app: `logAccessDecision` ran a full state hydration *plus* a
rewrite of the entire ever-growing `soc2AuditLogs` array **per denied request** — which,
on a public host, means per bot probe — serialized on the global mutation queue. Nothing
anywhere backed off a failing dependency, and failed reads were never cached, so every
caller re-paged the whole table at network speed.

**What shipped.**

- **Denial audit is now one conditional INSERT.** `logAccessDecision` calls
  `store.claimCollectionItems("soc2AuditLogs", [audit])` — no state read, no mutation-queue
  slot. Cost per denial no longer grows with total denials ever logged.
- **A process-wide write budget for denials.** The pre-existing per-key dedup cannot bound
  a scanner sweeping thousands of *distinct* paths (each path is a fresh key), so a fixed
  window caps denial persistence at **30/min** (`ACCESS_DENIAL_LOG_MAX_PER_MINUTE`).
  Denials beyond the budget are **still denied** — they are simply not individually
  persisted. Authorization behavior is unchanged; only the logging volume is bounded.
- **Circuit breaker + outbound request gate** — new `scripts/supabase-backoff.mjs`
  (`createSupabaseCircuit` at `:56`, `createSupabaseRequestGate` at `:145`): 8 consecutive
  failures open the circuit, 2s cooldown doubling to 60s, one half-open trial; 16
  concurrent / 200 queued with a clean 503 on overflow. Every Supabase REST request in
  `scripts/storage.mjs` now runs through both. While open, the circuit fast-fails with
  **zero network traffic**.
- **Three-state health probe** (see §4) — cached 30s, single-flight, never self-retrying,
  2.5s budget, reported through `/api/version` (`supabaseState`) and
  `/api/health/supabase` (`state`).
- **Proposed, not executed:** `supabase/migrations/20260724_001_perf_updated_at_index_and_statement_timeout.sql`
  — an `updated_at DESC` index for the state-cache signature probe (30.3ms → 0.13ms on a
  local 60,000-row reproduction, labeled as local plan evidence) and a 10s `service_role`
  `statement_timeout`. Additive only; nothing in the app runs it.
- **Tests:** `scripts/test-supabase-backoff.mjs` (registered in `npm test`); three existing
  suites updated to the new probe/denial contracts.

## 2. PR #117 — bound hydration, exclude the audit ledgers (`685feec`, 2026-07-25)

**What went wrong.** Production re-saturated within minutes of the service resuming. The
#116 budget capped denial writes at 30/min, but each of those inserts still (a) moved the
state-cache **signature** and (b) bumped the in-process **write generation** — so the state
cache was invalidated up to 30×/minute and every subsequent read re-paged the entire
`leos_core_records` table, a payload dominated by the uncapped pre-#116 `soc2AuditLogs`
history. A denial-write → invalidation → full-re-page loop.

**What shipped.**

- **Audit ledgers excluded from the hot path.** `hydrationExcludedCollections =
  {soc2AuditLogs, auditEvents}` (`scripts/storage.mjs:252`). They never appear in the
  `readState()` / state-cache graph (hydrated as a deterministic `[]`); they do not move
  the cross-process signature probe (`hydrationExclusionFilter`, `:255`); and when written
  alone they do not bump the full-state write generation. They remain **registered,
  writable, and readable** via explicit `readCollections([...])` — exclusion is strictly a
  hydration concern, not a loss of the ledger.
- **Targeted hot-path reads.** `/api/boot-state` reads exactly
  `BOOT_STATE_READ_COLLECTIONS` (new `scripts/boot-state-read-collections.mjs`, 35
  collections) and `/api/today/summary` reads exactly `TODAY_SUMMARY_READ_COLLECTIONS`
  (`scripts/company-memory-projector.mjs`) — both via `store.readCollections`, never
  `store.readState()`. First paint and Today can no longer page the whole table however
  large the ledgers grow. A maintenance rule enforced by `test-hydration-bounds.mjs`
  requires any new `state.<collection>` read in those builders to be added to the list.
- **Retention prepared, NOT run.** `supabase/maintenance/20260725_soc2_audit_log_retention.sql`
  archives every `soc2AuditLogs` row to a timestamped, service-role-only table, verifies
  the copy row-for-row, trims live rows to 90 days, and prints before/after counts. If
  verification fails the transaction aborts and nothing is deleted. It lives in
  `maintenance/`, not `migrations/`, because it is a one-off operator action on data.
  **Roger runs it manually; it has not been run.**
- **Tests:** new `scripts/test-hydration-bounds.mjs` (9 checks, in `npm test`);
  `test-state-cache-coherence.mjs` extended for excluded-ledger semantics.

## 3. PR #118 — serialize mutations, preserve read capacity (`fdbc334`, 2026-07-25)

**What went wrong.** ~45 concurrent mutation RPCs waiting on per-record advisory
transaction locks. The application had **two independent serializers and one hole**:
storage's `writeQueue` serialized `writeState`/`writeCollections`; preview-server's
`serializeStateMutation` serialized most route handlers; and `writeChanges` called
`supabaseRestRequest` **directly, on neither**. Two process-local conventions cannot
enforce a global invariant. Worse, one shared gate and one shared breaker meant a
lock-blocked write convoy consumed the slots reads needed, and write timeouts opened the
single breaker — which then **rejected healthy reads** and surfaced as "Supabase
disconnected" when reads were fine.

**What shipped.**

- **One FIFO core-mutation executor** (`scripts/storage.mjs:653–740`): at most **1 active**
  `rpc/leos_apply_core_mutations` per process, **32 queued**, immediate rejection with zero
  network when saturated (`SupabaseWriteQueueSaturatedError`, 503, `:628`), and a
  pre-network deadline shed for work that waited past its safe window
  (`SupabaseWriteQueueExpiredError`, 503, `:639`, default 20s). A failed operation settles
  only its own caller and never bricks the queue. **Nothing is retried** — a timed-out
  mutation may have committed, so resubmitting is a duplicate-write risk, not a recovery.
  Deliberately a plain array + pump loop rather than a promise chain, so "reject when full"
  and "expire before sending" are expressible.
- **The bypass is closed structurally.** `submitCoreMutations` (`:815–828`) is the single
  place in application code that may name the RPC, and
  `test-supabase-mutation-serialization.mjs` asserts that structurally. `writeChanges` now
  goes through it.
- **Separate read and write gates and breakers** (`:374–400`): a write convoy can consume
  at most the write gate, never a read slot; write timeouts open only the write breaker;
  and because the health probe is a read, a saturated write path can no longer report the
  database as disconnected. Write gate defaults: 4 concurrent / 64 queued
  (`SUPABASE_MAX_CONCURRENT_WRITES`, `SUPABASE_MAX_QUEUED_WRITES`). Timeouts,
  authentication, RLS, and service-role handling are unchanged.
  `supabaseCircuitSnapshot()` keeps its old top-level shape (the **read** circuit) and
  reports the write path alongside it, never merged into it.
- **Boot analytics write removed.** The automatic initial-route and hashchange Discovery
  Analytics persistence is gone
  (`src/server/controllers/discovery-analytics-controller.mjs`), so a passive load performs
  zero durable writes. `tests/browser/passive-boot-write-free.spec.mjs` proves it from
  outside the process: a real Chromium session against the real server on the real Supabase
  code path, pointed at a fake PostgREST endpoint, asserting **zero**
  `rpc/leos_apply_core_mutations` calls across boot, Today, four API reads, and 30s idle.
  Note for the record: the boot write was **not** the RPC behind the convoy — it was found
  by the broader "zero durable writes of any kind" assertion.
- **PII-free mutation telemetry** (`storage.mjs:758–811`): one structured
  `supabase_core_mutation` line per attempt with `requestMethod`, sanitized `route` (new
  `scripts/request-context.mjs`), `operationClass`, `mutationCount`, registry-validated
  collection **names**, `requestBytes`, process identity, `queueDepth`, `queueWaitMs`,
  `executionMs`, `outcome`, `errorCode`. The allowlist is exhaustive by construction — the
  object is built field by field from primitives, never spread from a payload — so it
  carries no payloads, item IDs, names, email addresses, message bodies, tokens,
  credentials, cookies, or headers. Error **codes** only, never messages (Supabase error
  details can echo payload fragments). Disable with `SUPABASE_MUTATION_TELEMETRY=0`.
- **Gated migration.** `supabase/maintenance/20260725_core_mutation_statement_timeout.sql`
  is **prepared, not executed, and evidence-gated**: it must not run until a live
  `pg_stat_activity` capture proves core-mutation backends stayed `active` past the
  client's timeout (i.e. the database kept holding advisory locks after the client gave
  up), and until the real worst-case duration of legitimate mutations is known so the
  ceiling is set rather than guessed.
- **Documented residual:** this bounds **one Node process**. Multiple Render instances — or
  a deploy overlap running old and new instances together — can each hold one active
  mutation. Verifying that against `pg_stat_activity` is on the post-merge checklist and is
  still open (`2026-07-25-production-verification.md`).

## 4. The probe's three states (introduced #116, unchanged since)

`supabaseHealthState(probeOk, circuit, checkedAt)` — `scripts/storage.mjs:1088–1099`:

| State | Condition | Meaning |
|---|---|---|
| `connected` | probe succeeded **and** the circuit is closed **and** no failure in the last 60s | Reads work |
| `degraded` | probe succeeded but the breaker is non-closed or failed recently, **or** the probe failed while storage traffic succeeded in the last 120s | Partial availability, either direction |
| `disconnected` | probe failed and nothing succeeded recently | Reads do not work |

Properties that matter for the Founder OS surfaces: the probe uses the **same client,
table, and request path** the storage layer uses, so it answers "can this app's own reads
work" rather than pinging a separate endpoint; it is cached (default 30s,
`SUPABASE_HEALTH_TTL_MS`, clamped 250ms–5min), single-flight across concurrent callers,
short-budgeted (2.5s) and **never self-retrying**; and since #118 it reads the **read**
circuit only (`:1129–1133`), so a convoyed write path can no longer report the database as
disconnected. Exposed as `supabaseState` on `/api/version` and `state` on
`/api/health/supabase`.
